## 1. EXECUTIVE SUMMARY

RAI (Reasoning Artificial Intelligence) is a universal productivity companion for anyone who struggles with self-discipline — students, freelancers, professionals, entrepreneurs, and anyone managing complex personal goals. It solves the "watcher dependency" problem by becoming an ever-present AI coach that plans, monitors, blocks, motivates, and adapts to the user's emotional and cognitive state in real time.

**What makes RAI different from every other productivity app:**
- It does not just list your tasks — it automatically schedules them into your day based on your energy, habits, and deadlines.
- It learns when you are most likely to get distracted (your personal danger zone) and sends a smart push notification *before* you open Instagram, not after.
- It categorizes your tasks intelligently — whether you're studying Physics, building a startup, going to the gym, or writing a novel.
- It works for anyone, not just students.

**Tagline:** *"Your AI coach that never lets you quit."*

## 6. PRIORITY #1 — AUTO-SCHEDULER ENGINE

> This is the most important feature in the entire app. If this works brilliantly, users will trust RAI with their day. If it schedules poorly, they will uninstall within 48 hours.

### 6.1 Philosophy

The scheduler must feel like a thoughtful human assistant, not a calendar optimizer. It must:
1. Respect human energy patterns (not just clock time)
2. Learn from the user's actual behavior (not just their stated preferences)
3. Protect the user from overcommitting
4. Adapt in real-time when things go wrong (task skipped, mood is low, day ran long)
5. Explain its decisions in plain English

### 6.2 Scheduler Inputs

```typescript
interface SchedulerInput {
  // User profile constraints
  sleepStart: string;           // "23:00"
  sleepEnd: string;             // "07:00"
  wakeBuffer: number;           // minutes after wake before first task (default: 30)
  sleepBuffer: number;          // minutes before sleep for wind-down (default: 45)
  mealTimes: MealSlot[];        // [{ name: "Lunch", start: "13:00", duration: 45 }]
  preferredWorkHours: string[]; // ["09:00-12:00", "16:00-19:00"]
  
  // Existing calendar
  existingTasks: ScheduledTask[];
  existingEvents: CalendarEvent[]; // from Google Calendar sync (post-MVP)
  
  // Task to schedule
  newTask: {
    title: string;
    category: TaskCategory;     // auto-detected by categorizer
    estimatedMinutes: number;
    deadline: string;           // ISO datetime
    priority: 1 | 2 | 3 | 4;   // 1=low, 4=urgent
    difficulty: 1 | 2 | 3 | 4 | 5;
    moodSensitive: boolean;
    dependencies: string[];     // task IDs that must be done first
    isRecurring: boolean;
    recurrenceRule?: RecurrenceRule;
    preferredTimeOfDay?: "morning" | "afternoon" | "evening" | "any";
    isQuickTask: boolean;       // true if <= 15 min → scheduler may batch these
  }
  
  // Behavioral data (learned over time)
  userEnergyProfile: EnergyProfile;
  historicalCompletionRates: CompletionRateByHour;
  dangerZoneHours: number[];    // hours with high distraction history
}
```

### 6.3 Energy Profile Model

The scheduler does not use hardcoded rules like "morning is +20 points." It builds a personal energy profile for each user over the first 7 days.

```typescript
interface EnergyProfile {
  // Learned from focus session completion rates per hour
  energyByHour: Record<number, number>; // hour (0-23) → energy score (0-100)
  
  // Learned from task completion rate per category
  categoryBestHours: Record<TaskCategory, number[]>;
  
  // Circadian defaults (used before enough data exists)
  chronotype: "morning" | "intermediate" | "evening";
  
  // Estimated from actual vs planned durations
  durationAccuracyFactor: number; // 1.0 = perfect. 1.3 = user underestimates by 30%
  
  // Days with historically low performance
  weakDays: ("Mon" | "Tue" | "Wed" | "Thu" | "Fri" | "Sat" | "Sun")[];
}
```

**Cold Start (Days 1–7):** Use chronotype selected during onboarding + standard circadian defaults.  
**Warm Model (Days 7–30):** Blend defaults with observed patterns.  
**Full Model (30+ days):** Fully personalized per user.

### 6.4 Slot Scoring Algorithm

```
For each available slot (start_time, duration):

  BASE_SCORE = 50

  + energyByHour[slot.hour] × 0.4           // personal energy weight (max +40)
  + preferredWorkHour bonus × 15             // user stated this time is preferred
  - dangerZone penalty × 20                  // this hour is historically high distraction
  + priority urgency score (4→+25, 3→+10, 2→0, 1→-10)
  + deadline proximity factor                // closer deadline = prefer sooner slot
  - context switch penalty                   // different category than adjacent tasks: -8
  + same category bonus                      // batching similar tasks: +5
  - slot fragmentation penalty               // slot is too short relative to task: -15
  + mood adjustment                          // if current mood < 3, prefer easier tasks
  + dependency bonus                         // prerequisite task completed: +20
  
  FINAL_SCORE = clamped(BASE_SCORE, 0, 100)
```

The highest-scoring available slot wins.

### 6.5 Long Task Splitting

- If `estimatedMinutes > 90`: split into sessions
- Session max: 90 min for difficulty ≥ 4, 120 min for difficulty ≤ 3
- Mandatory break between sessions: 10–15 min (stored as a break block, not a task)
- Sessions are scheduled on the same day if possible, else across consecutive days with smart sequencing

### 6.6 Buffer Insertion

- 15-min buffer before and after every scheduled task (prevents cascade failures)
- Tasks that historically run long (duration accuracy factor > 1.2) get a `× durationAccuracyFactor` time allocation automatically

### 6.7 Mood Adaptation (Real-Time Rescheduling)

When a mood check-in returns mood ≤ 2:
1. Identify tasks scheduled for the next 3 hours with difficulty ≥ 4
2. Offer to move them to the next high-energy slot
3. Replace with easier tasks from the unscheduled pool
4. If no easier tasks exist, suggest a structured break or a "quick wins" session (tasks ≤ 15 min)

### 6.8 Overload Detection

Before confirming any schedule, the scheduler runs an overload check:

```
IF total scheduled minutes > (available minutes × 0.85):
  → Warn: "Your day is packed at 92% capacity. I recommend removing [lowest priority task]."
  → Show capacity bar
  → Offer: [Auto-remove lowest priority] [Keep and risk overrun] [Extend to tomorrow]
```

### 6.9 Quick Tasks (< 15 min)

Tasks under 15 minutes are "quick tasks." The scheduler:
- Batches them into "quick wins" blocks (e.g., a 30-min block containing 2–3 quick tasks)
- Prefers to place quick wins blocks in naturally low-energy transition periods (post-lunch, early evening)
- Never splits a quick task across days

### 6.10 Recurring Task Logic

```typescript
interface RecurrenceRule {
  frequency: "daily" | "weekly" | "weekdays" | "custom";
  daysOfWeek?: number[];       // 0=Sun, 6=Sat
  endDate?: string;
  skipDates?: string[];        // user-marked exceptions
}
```

Recurring tasks auto-schedule for future instances. If a slot conflict arises, the scheduler finds the next available slot within ±2 hours of the usual time.

### 6.11 Dependency Chains

```
Task B depends on Task A → Task B cannot be scheduled before Task A's earliest completion time.
Scheduler enforces this silently.
If Task A is delayed → all dependent tasks cascade-reschedule automatically.
User is notified: "Completing 'Read Chapter 1' unlocks 'Write Summary'. I've adjusted your schedule."
```

### 6.12 Scheduler Output & Explanation

Every scheduling decision produces a human-readable rationale:

```
"I scheduled 'Workout' at 7:00 AM because your energy data shows you're 40% more likely 
to complete physical tasks in the morning. It's your highest-energy window."

"I split 'Study Machine Learning' into two 90-min sessions because 3 hours in one block 
has a 68% dropout rate for difficulty-5 tasks based on your history."

"I moved 'Client Call Prep' to 4:30 PM — it conflicts with your lunch buffer and you 
have a dependency: 'Review Brief' must finish first."
```

These rationales appear as tappable chips on scheduled task cards.

## 7. PRIORITY #2 — DANGER ZONE & PUSH NOTIFICATION SYSTEM

### 7.1 Danger Zone Detection

The danger zone is **not hardcoded.** It is computed fresh every week per user from their actual UsageStats data.

```typescript
interface DangerZoneProfile {
  // Hours of day where user has consistently high distraction app usage
  dangerHours: number[];          // e.g., [14, 15, 22, 23]
  
  // The top distraction apps for this user
  topDistractionApps: string[];   // package names, ranked by time spent
  
  // Day-of-week patterns
  weakestDay: string;             // e.g., "Saturday"
  
  // Doom loop patterns (sequential app switching)
  doomLoopSequences: string[][];  // e.g., [["Instagram", "YouTube", "TikTok"]]
  
  // Confidence in the model
  dataPoints: number;             // number of days of data collected
  lastUpdated: string;
}
```

**Algorithm:**
1. Every Sunday at 6 AM, aggregate 7 days of UsageStats
2. For each hour of the day, compute average distraction minutes
3. Hours where avg distraction minutes > (avg productive minutes × 1.5) → flagged as danger hours
4. Rank hours by danger score (0–100)
5. Store top 3 danger hours as the user's personal danger zone
6. Show danger zone as an annotated band on the calendar and heatmap

**First 7 Days:** Use global averages (2–4 PM and 9–11 PM are statistically high distraction for most users) as bootstrap defaults. Display as "estimated danger zone" with a disclaimer. Replace with personal data after 7 days.

### 7.2 Real-Time Risk Score

The Procrastination Risk Score is computed every 5 minutes in a background task (via `expo-task-manager` + `expo-background-fetch`).

```typescript
interface RiskSignals {
  // 0-20 points each, total = 0-100
  pickupFrequency: number;      // phone pickups in last 30 min vs. baseline
  appSwitchRate: number;        // rapid app switching → doom loop indicator
  timeSinceLastFocus: number;   // minutes since last productive action
  dangerHourScore: number;      // how deep into the danger zone is this hour?
  missedTaskCount: number;      // tasks that were due but not started
  currentMoodPenalty: number;   // low mood → higher risk
}
```

If `totalRiskScore > 70` → trigger intervention notification.

- Notification timing respects sleep hours (no notifications between sleepStart and sleepEnd)

## 8. PRIORITY #3 — SCREEN TIME TRACKING (NATIVE MODULE)

### 8.1 `expo-usage-stats` Module

This module wraps Android's `UsageStatsManager`.

```typescript
// Module API (TypeScript)
interface ExpoUsageStats {
  // Check if permission granted
  hasPermission(): Promise<boolean>;
  
  // Open system settings to grant permission
  requestPermission(): Promise<void>;
  
  // Get usage stats for a time range
  getUsageStats(startMs: number, endMs: number): Promise<AppUsageRecord[]>;
  
  // Get hourly breakdown for today
  getHourlyBreakdown(): Promise<HourlyUsage[]>;
  
  // Get app category classification
  getAppCategory(packageName: string): Promise<AppCategory>;
}

interface AppUsageRecord {
  packageName: string;
  appName: string;
  totalMinutes: number;
  lastUsed: number;
  firstUsed: number;
  launchCount: number;
}

interface HourlyUsage {
  hour: number;           // 0-23
  distractionMinutes: number;
  productiveMinutes: number;
  totalMinutes: number;
}
```

**Update Frequency:** Every 15 minutes via `BackgroundFetch`. Not real-time (battery preservation).

**App Classification:**

Apps are classified into two buckets automatically:


## 10. TASK AUTO-CATEGORIZATION ALGORITHM

### 10.1 Philosophy

Tasks are **never locked** to a fixed set of categories like "Physics / Chemistry / Maths." The system detects the right category from the task title and context, generates new categories as needed, and only groups tasks that genuinely belong together.

### 10.2 Category Taxonomy (Dynamic, Not Hardcoded)

**Tier 1 — Global Categories (always available):**
```
Work          → Reports, meetings, client work, deadlines
Learning      → Courses, studying, reading, practice
Health        → Gym, running, meditation, sleep hygiene
Creative      → Writing, design, music, video, art
Personal      → Errands, admin, family, home
Finance       → Budget, invoices, investments, bills
Social        → Events, calls, messages, networking
Side Project  → Building, coding, research
```

**Tier 2 — Domain-Specific Sub-Categories (user-generated, AI-detected):**
```
If user has "Physics numericals" and "Physics revision" → auto-create "Physics" sub-category under Learning
If user has "Client A proposal" and "Client A call" → auto-create "Client A" grouping under Work
If user has "Leg day", "Chest day" → auto-create "Gym" sub-category under Health
```

These sub-categories appear as filter chips on the Tasks screen only once there are 3+ tasks in a sub-category.

### 10.3 Categorization Algorithm

```typescript
async function categorizeTask(title: string, context: UserContext): Promise<TaskCategory> {
  
  // Step 1: Keyword matching (fast, no AI call)
  const keywordMatch = matchKeywords(title, CATEGORY_KEYWORD_MAP);
  if (keywordMatch.confidence > 0.85) return keywordMatch.category;
  
  // Step 2: Pattern matching against user's existing tasks
  const historicalMatch = matchAgainstHistory(title, userTaskHistory);
  if (historicalMatch.confidence > 0.80) return historicalMatch.category;
  
  // Step 3: Claude API call (only if steps 1-2 are inconclusive)
  const aiCategory = await claudeClassify(title, {
    existingCategories: userContext.usedCategories,
    userGoalType: userContext.goalType,
    recentTasks: userContext.last10Tasks,
  });
  
  return aiCategory;
}
```

**Keyword map examples (partial):**
```
"gym", "workout", "run", "yoga", "meditation", "swim" → Health
"report", "meeting", "client", "proposal", "invoice", "deadline" → Work
"read", "study", "revise", "practice", "course", "lecture" → Learning
"write", "design", "draw", "compose", "edit", "create" → Creative
"groceries", "call mom", "dentist", "laundry", "bills" → Personal
```

### 10.4 Category Color System (Dynamic)

Each category gets a color from a predefined palette. User can override. New auto-detected categories are assigned the next unused color.


## 12. GAMIFICATION SYSTEM

### 12.1 XP Formula

```
Task Completion XP = (difficulty × estimatedMinutes) / 8
Focus Session XP = minutesCompleted × 1.5
Streak Bonus XP = streakDays × 12
Achievement XP = flat reward per achievement (10–500 XP)
Mood Check-In XP = 10 XP (encourages emotional awareness)
Diary Entry XP = 25 XP (encourages reflection)
```

| 10 | 2,000 | Focused | Scholar | Professional |

## 16. NON-FUNCTIONAL REQUIREMENTS

### 16.1 Performance

| Metric | Target |
|---|---|
| Cold start | < 2 seconds on Snapdragon 720G, 4GB RAM |
| Calendar render (50 tasks) | < 100ms |
| Claude API response | < 2 seconds (skeleton loader after 500ms) |
| Screen time sync | Every 15 minutes (not real-time) |
| Widget update | Every 15 minutes + on key events |
| Risk score calculation | Every 5 minutes (background) |
| Scheduler (new task) | < 500ms |
| Scheduler (full day rebuild) | < 2 seconds |

### 16.2 Reliability

- **Local-first:** All core features work fully offline. Supabase sync is opportunistic.
- Background services survive device reboot via `BootReceiver` (expo-boot-receiver module)
- `WorkManager` for all periodic tasks (battery-aware, guaranteed execution)
- Task scheduling state is never lost — every change is immediately persisted to Room before any UI update

### 16.3 Security

- Claude API key: stored in EAS Secrets, proxied via Supabase Edge Function — never in client bundle
- User data: encrypted at rest via SQLCipher (expo-sqlite with encryption key from expo-secure-store)
- Supabase auth: JWT, RLS enforced at database level
- No PII sent to Claude API except first name and anonymized task metadata
- UsageStats: read-only, never sent to any server (processed entirely on-device)

### 16.4 Accessibility

- Minimum touch target: 48dp × 48dp
- Content descriptions on all icons and images
- TalkBack support for all interactive elements
- Color contrast ratio ≥ 4.5:1 for all text
- Font scaling support up to 200%
- No color-only information (icons always accompany color coding)

### 16.5 Battery & Resource Efficiency

- UsageStats read: batched, not streaming
- AccessibilityService: monitors package names only, not screen content
- Background location: not used (GPS only used if user opts in for location-based task context)
- Network requests: batched and deferred when on low battery
- AI API calls: cached for identical inputs within a 5-minute window

## 17. USER FLOWS

### 17.1 First-Time User Flow

```
Install
→ Splash (2s)
→ Onboarding Q1–Q7 (adaptive, voice-capable)
→ Permissions Setup (sequential, skippable)
→ Home Screen (pre-populated sample schedule for today)

→ Scheduler runs → Calendar shows task placed at optimal slot
→ Scheduler rationale chip: "Placed at 9 AM — your highest energy window"
→ Widget setup prompt (if Android 12+)
→ Day 1 complete
```

### 17.2 Daily Active User Flow

```
Morning notification (wake time + 15min): "Good morning! 5 tasks, first up: Client Call at 9AM"
→ Open app → Mood check-in (takes 5 seconds)
→ Home screen → review schedule
→ Tap first task → Start Focus Timer (50min deep work)
→ Timer completes → haptic cascade → XP awarded → task marked done
→ Next task auto-starts after break countdown
→ 2PM: Danger zone starts
→ Risk score hits 72 → Push notification: "⚠️ Danger zone active. You have 'Read Chapter 3' at 3PM. Lock in now?"
→ User taps [Start Task] → Focus timer opens
→ 9PM: Evening report notification
→ Opens app → sees "4/5 tasks done. 1h 20min saved from distraction. Better than yesterday."
→ Diary Chat (2 min) → AI generates daily summary
→ RAI Score updates → streak preserved → close app
```

### 17.3 Distraction Interception Flow

```
User opens Instagram (blocked app during scheduled work block)
→ expo-accessibility-overlay detects package switch
→ Full-screen friction overlay appears:
   - 10-second countdown
   - "Your Client Proposal is waiting" (shows active task)
   - [🚀 Back to Work] [🎵 Play my motivation] [⏸ I need 15min break]
→ Path A: User taps [Back to Work] → overlay dismisses → RAI reopens
→ Path B: User taps [15min break] → timer set → Instagram accessible → timer ends → notification "Break over. Ready to resume?"
→ Path C: User taps skip (3rd override today) → must type: "I am choosing distraction because..."
→ Override logged → evening report shows: "You overrode focus 3 times between 2–4PM. That's your pattern."
```

### 17.4 Danger Zone Alert Flow

```
Background task runs every 5 minutes
→ Detects: current hour = 14 (in danger zone), risk signals elevated
→ Risk score = 78 → threshold exceeded
→ Notification sent (DANGER_ZONE channel): 
   "⚠️ Your danger zone just started. You usually spend 47min on Instagram now. 
    'Client Proposal' is next. Start now?"
→ Actions: [🚀 Start Focus] [⏰ Snooze 10min] [📅 Reschedule]
→ User taps [Start Focus] → app opens → Focus Timer auto-loads next task
→ Intervention logged as successful
```

## 20. IMPROVEMENTS & ROADMAP

### 20.1 Improvements Over Original PRD

These are meaningful upgrades beyond the v1 PRD, worth building into MVP:

| # | Improvement | Why It Matters |
|---|---|---|
| 1 | **Personal danger zone detection** (vs. hardcoded 2–4 PM) | Every user is different. A night owl's danger zone is 11 PM, not 2 PM. Personalization = trust. |
| 2 | **Circadian energy model** (vs. generic morning bonus) | The scheduler learns your actual performance patterns — more accurate placement = higher acceptance rate. |
| 3 | **Duration learning** (actual vs. estimated tracking) | Users consistently under- or overestimate. After 2 weeks, the scheduler automatically corrects for this. No other app does this. |
| 4 | **Dependency chains** | Real tasks depend on each other. Supporting this makes RAI usable for complex projects, not just simple to-dos. |
| 5 | **Overload detection** (capacity protection) | Prevents the #1 cause of productivity app abandonment: the user puts in 12 tasks, completes 3, feels like a failure. |
| 6 | **Quick task batching** | Short tasks (< 15 min) should be grouped, not scattered. Prevents context switching fatigue. |
| 7 | **General-purpose categories** (vs. subjects only) | Opens the app to all users, not just exam students. 5× the addressable market. |
| 8 | **Tier-2 dynamic sub-categories** | Emerges from the user's own data. Feels magical — the app learned that "Client A" is its own category without being told. |
| 9 | **Notification rate limiter** | The biggest cause of notification opt-out is over-notification. Rate limiting preserves the channel for critical alerts. |
| 10 | **Rich notification actions** | Users can start focus, snooze, or reschedule directly from the notification — without opening the app. Reduces friction to action. |
| 11 | **Scheduler rationale in plain English** | Users trust systems they understand. Showing "why" each task was placed there dramatically increases schedule adherence. |
| 12 | **Home screen widget** | Passive presence. Users see their schedule without opening the app. 40%+ widget install rates correlate with D30 retention. |
| 13 | **AMOLED theme** | ~60% of Indian Android users have AMOLED screens. True black saves battery. Strong signal of quality. |
| 14 | **API key proxied via Edge Function** | Client-side API key exposure is a critical security hole. Non-negotiable for production. |
| 15 | **Mood via inline notification action** | 4-tap mood logging from notification (no app open needed) dramatically increases mood check-in rates. |

## APPENDIX C — Key Glossary

| Term | Definition |
|---|---|
| RAI Score | Composite productivity score (0–1000): Consistency + Focus + Planning + Recovery + Social + Growth |
| Focus Score | Daily score (0–100) measuring task completion and distraction avoidance |
| Danger Zone | Hours of day where a user has a personal history of high distraction, computed from 7+ days of UsageStats |
| Energy Profile | Personalized hourly energy model built from focus session completion rates |
| Duration Accuracy Factor | Ratio of actual to estimated task duration, learned per category over time |
| Soft Deadline | Task deadline minus sleep buffer, used by scheduler as the latest possible slot |
| Quick Task | Any task ≤ 15 minutes; batched into "quick wins" blocks rather than scheduled individually |
| Doom Loop | Rapid app switching pattern (e.g., Instagram → YouTube → Instagram) indicating distraction spiral |
| Mood Sensitive | Task flag: if user mood ≤ 2 at scheduled time, AI offers to reschedule or swap |
| Scheduler Rationale | Plain-English explanation of why the AI placed a task in a specific slot |
| MCP Server | Model Context Protocol layer handling Supabase auth and queries |
| Comeback Mode | Reduced 3-day schedule (max 2 easy tasks/day) for users re-entering after a gap |
